# Scarp VS Code: Local workspace navigation (development)

This document describes the compiler-free editor/navigation features developed
for the experimental Scarp VS Code extension. It is a guide for maintainers,
reviewers and test contributors, not a replacement for the published compiler
reference. Editor lexical results must never be advertised as semantic proof.

## Supported user workflows

### Readable Scarp source files

Open a Scarp file ending in .srp. No installation step is required for:

1. Code folding of multiline blocks, arrays, parenthesized calls, comments
   and consecutive valid import declarations.
2. Named folds using // #region and // #endregion comments.
3. Native Expand Selection through a token, string, nested expression, block,
   physical line and full document.
4. The existing TextMate syntax highlighting and declaration Outline.

Folding and selection are static source-text operations. The file is not saved,
formatted, evaluated, verified or sent to an external program by these actions.
Both continue working inside Restricted Mode.

### Open local imported modules

A complete top-level Scarp import declaration can display a clickable path:

    import "lib/math.srp" as math;

The extension only links to an ordinary local file already present within the
active VS Code workspace folder. The link is available only in a trusted
workspace. A link cannot be created from a function-local pseudo-declaration,
a comment, a string literal, an unsupported escape, or a missing file.

The importer does not guess language semantics. For example, it does not
resolve dynamically constructed paths or automatically install dependencies.
The actual Scarp compiler is the authority for valid imports.

### Browse imports in a nested workspace

Open the Command Palette and select:

    Scarp: Browse Local Workspace Imports

The command asks for a workspace root when multiple local roots are open
and there is no active source file identifying one of them. It enumerates
only Scarp source files beneath the selected root. It builds an in-memory
lexical import graph and displays a Quick Pick of indexed modules.

Choose an ordinary source to open it in VS Code. Choose the dedicated
dependency report item to inspect:

- Indexed modules and their incoming/outgoing import counts.
- Lexical imports with source offsets and aliases.
- Missing references within the selected snapshot.
- Syntactic import cycles and unreferenced roots.
- Source metrics (lines, functions, file sizes and delimiter depth).
- Files that were skipped for size, encoding or path safety reasons.

The report opens as an unsaved Markdown editor buffer. It does not write a
report into the project, publish anything or launch the Scarp compiler.
It is a snapshot of disk content at the time the user selects the command;
unsaved buffer changes are not silently mixed with disk snapshots.

### Discover multiple Scarp projects

Open the Command Palette and select:

    Scarp: Browse Nested Workspace Projects

The picker discovers both compiler manifest generations:

- Lowercase scarp.project: the modern declarative v2 format generated by the
  published alpha.20 compiler and later compatible releases.
- Uppercase Scarp.project: the historical v1 manifest readable by the
  compiler for compatibility with earlier Scarp projects.

A workspace may contain separate project folders, such as:

    Scarp-Practice/
      basic_integer/
        scarp.project
        src/main.srp
      basic_tuple/
        scarp.project
        src/main.srp
        tests/tuple.srp
      experiments/
        legacy-project/
          Scarp.project
          src/main.srp

The project picker identifies each recognized project independently. It
offers three explicit, read-only navigation choices:

1. Open Project Entry.
2. Open Project Manifest.
3. Browse Project Source Tree.

The nested source tree displays folders and .srp files with source counts.
Selecting a folder navigates deeper; Parent folder navigates one level up.
Selecting a file opens the actual ordinary source after a final containment
check. No project is run, initialized, downloaded or modified by the picker.

## Compiler compatibility boundaries

These conveniences are lexical and are compatible with older compiler source
files. No compiler process is launched merely to display folding ranges or
selection expansions. Opening a source through a Quick Pick is also not an
execution action.

The project manifest catalog intentionally recognizes a narrow subset of
compiler-written scaffold layouts. It is not a full manifest parser or
validator and can reject a legitimate future compiler format. An unsupported
manifest should be inspected through the installed Scarp compiler rather than
loosening path and text validation speculatively.

The import graph is similarly not a dependency resolver. It cannot infer
conditional code, semantic visibility, transitive symbol names or runtime
behavior. An import marked missing may simply be outside the selected
snapshot. Use explicit Scarp Verify and project module inspection for
compiler-authoritative results.

## Resource limits and performance

The structural editor scanner has hard default bounds:

| Resource | Default limit |
| --- | ---: |
| Source text per structural scan | 2,000,000 UTF-16 code units |
| Lexical tokens per structural scan | 120,000 |
| Nested bracket depth | 256 |
| Folding ranges returned | 5,000 |
| Expand Selection ancestors returned | 48 |
| Cached source snapshots | 12 |
| Total cache source-text budget | 12,000,000 estimated bytes |
| Workspace import graph files | 512 |
| Workspace source file read | 1,000,000 bytes |
| Total workspace source bytes | 16,000,000 |
| Import graph edges | 4,096 |
| Project manifest previews | 256 |
| Project manifest bytes | 4,096 |
| Project tree file entries | 512 |
| Project tree nesting | 32 path segments |

The cache uses the editor document identity, text version and exact source
text to prevent stale folding and selection ranges. Older cache entries
are evicted in least-recently-used order. Closed documents release their
cached source. There is no background timer, network polling or compiler
capability probe in these providers.

A limit failure should suppress the corresponding editor-only feature or
show a clearly bounded inventory issue. It must not silently fall back to
unbounded recursion or scan the entire drive.

## Security and trust model

Opening a Scarp file is not equivalent to allowing it to execute. These
features keep that separation through several independent controls:

- Restricted Mode permits local source folding and selection, but suppresses
  trusted-workspace import links and on-demand disk explorers.
- Both workspace commands recheck trust before file enumeration.
- Local project paths are matched against an explicitly selected workspace
  root; multiple roots are not automatically combined.
- Scarp source references must be relative .srp paths, not URLs, absolute
  paths, drive paths, traversal paths or encoded path components.
- Real filesystem paths are rechecked against the canonical workspace root,
  so symlinked paths escaping the selected root are refused.
- Source documents opened from pickers are revalidated after the user makes
  a choice, preventing stale Quick Picks from opening a replaced symlink.
- The import report escapes user-controlled Markdown table and label content
  rather than treating filenames as executable command links.
- Source bytes are read with strict UTF-8 decoding and bounded lengths.
- No external process, shell, network client or package installer is used.

The checks do not provide an OS sandbox and do not guarantee that another
process cannot change files. They only constrain the editor extension's own
read-only navigation actions.

## Reliability and cancellation

Folding and selection run synchronously on bounded in-memory editor content.
No asynchronous filesystem action is needed. Their scanners never execute
Scarp statements or import another module.

On-demand workspace discovery uses VS Code progress cancellation and passes
an abort signal to the local source inventory where applicable. A cancelled
request does not show a stale module picker. Project discovery also checks
cancellation and Workspace Trust throughout its inventory phase.

A user may modify a file after a graph report is generated. The report
explicitly describes itself as a snapshot; it is not live diagnostics.
Files selected later are checked against the current filesystem state.

## Manual quality-assurance scenarios

Verify the following in a supported development VS Code Extension Host:

1. Open a standalone Scarp source and fold a multiline function body.
2. Fold nested array and tuple parentheses without losing outer ranges.
3. Fold two // comment lines, leaving an inline code comment unfolded.
4. Fold a named // #region and verify a missing end marker does not invent
   a fold.
5. Expand Selection inside a quoted string containing braces and Unicode.
6. Expand Selection inside a nested tuple expression.
7. Edit the file, then immediately expand again; no stale selection offsets.
8. Open a nested Scarp folder containing several independent source files.
9. In a trusted workspace, follow a valid local import link.
10. Confirm imported paths containing traversal or backslashes are not linked.
11. Confirm an import targeting a symlink outside the workspace is not linked.
12. Browse an import graph with a missing module and inspect its report.
13. Browse an import graph with an A-to-B-to-A cycle.
14. Open a modern scarp.project beside a legacy Scarp.project in another
    nested project, then use the project picker.
15. Choose a project entry file and confirm the file opens without running.
16. Browse deep source directories and use Parent folder navigation.
17. Open a multi-root workspace; confirm selection targets only one root.
18. Attempt a workspace explorer in Restricted Mode and confirm no disk
    enumeration or compiler execution occurs.
19. Test a source larger than the structural scan limit; VS Code remains
    responsive and TextMate coloring still works.
20. Run extension typechecking, linting, unit tests and the real Extension Host
    tests on each supported platform.

## Automated coverage

The repository's Node tests exercise:

- Source scanning, UTF-16 offsets, delimiters and regions.
- Folding range ordering, deduplication and explicit limits.
- Selection ancestor nesting and cancellation-safe empty behavior.
- Import links, path boundaries, symlinks and missing files.
- Module graphs, cycles, duplicate sources and bounded graph sizes.
- Nested project catalogs, manifest-format compatibility and file trees.
- Local filesystem inventories, strict UTF-8 and budget enforcement.
- Deterministic Markdown reports and Markdown escaping.
- Source metrics and version-scoped cache eviction.
- Package/extension security policy invariants.

The separate VS Code Extension Host tests cover native provider registration,
Restricted Mode and editor command behavior. Historical compiler integration,
download provenance and release publication gates remain separately required.

## Release and review policy

These development changes do not authorize extension publication. A
successful source PR merge does not by itself authorize a new GitHub tag,
Visual Studio Marketplace version or Open VSX publication. Continue using
the existing release qualification workflow and obtain explicit approval
for each pre-release candidate. A stable extension must not be published
before the Scarp compiler has a verified stable release.
